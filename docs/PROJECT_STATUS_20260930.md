## 什么已经统一，什么没有统一

统一控制流程：

1. 节点发现/地址选择，读取本机配对身份。
2. 成立经配对证书校验的控制TLS Session，交换资源目录并保活。
3. 任意一端发起具体资源使用，建立Source→Sink Route。
4. 资源所有者确认或使用该资源的记住授权；申请有限租约并协商参数。
5. 各Adapter准备专用数据端点、启动采集/接收/系统投影。
6. 回报实际运行证据；停止/撤权/断线按功能释放资源与租约。

Route是逻辑资源连接，不是一条承载所有字节的物理连接。控制TLS承载目录、
授权、设置、端点和少量启动消息；音视频、触点、IMU数据不经过该控制通道。
现有主路径以AdapterManaged整合成熟实现，而非把所有协议重写成统一媒体协议。
每种数据方向属于Port；节点没有固定全局server/client身份，但各功能仍有明确
Source/Sink方向。音频与显示的方向不能简单统称Android→Windows。

“连接一次”意味着已建立节点会话后，各功能无需重复填写地址、分别手工启动
旧应用；不意味着自动使用所有资源、不再授权，也不意味着只开放一个数据端口。
一个手柄使用操作还可能同时拥有正向输入和反向振动两个Route。

## 安全边界

控制链路使用配对TLS；触控板和振动有各自绑定的TLS数据链路。
原生音频UDP、手柄输入UDP、CAVC摄像头TCP不能被描述为全部已有CapyIO
应用层加密。显示沿用GameStream适配器安全契约，不能外推成统一TLS媒体面。
当前媒体实验路径面向已限定的Windows/Y700及Tailscale网络；Tailscale隧道
保护与应用层认证/加密是不同层次，不能因此宣称任意裸公网部署安全。

## 与原始预期仍有的差距

- 首次信任仍可见.cpi邀请生成/导入流程；尚未完整达到“任意一端发邀请，
  对方首次点允许即可完成信任”的普通用户体验。资源“允许并记住”不能代替首次配对。
- 已配对发现/连接和反向连接可用，但保留地址/监听/账号诊断入口；Android
  手动拨号仍有单有效配对节点限制。跨网段自动发现不是已完整验证的即开即用功能。
- Vue界面和主要操作已统一；Android原生全屏接收/输入页、Windows驱动与服务
  管理仍是平台实现，不能说所有平台代码完全相同。高级兼容入口尚未彻底清理。
- 全局多节点资源池、多人同时使用不同硬件、公平冲突管理及任意节点组合仍需
  专门产品化和实测；已有Port租约机制不等于完整多用户产品已交付。
- 手柄设置和显示协商已有双端机制，但不是所有硬件全部设置都实现双向同步。
- 驱动安装、相机注册、VIIPER/USB-IP依赖、后台Broker配置仍依赖已有环境，
  有些路径需要管理员启动。首次安装、生产签名、普通权限使用、自动升级尚未收尾。
- 本地完整调试包已生成并通过69文件完整性检查；签名APK是debug签名，不是
  正式发布签名。显示第三方组件公开分发所需许可证/NOTICE/对应源码工作仍待完成。
- 120FPS、显示运行中切画质和网络自适应码率属于后续增强，不阻塞当前初版功能验收。

## 建议下一阶段

1. 固化本次整合代码和当前验收基线，不再把“功能可用”与“正式发布”混称。
2. 优先首次信任简化、节点总开关与连接状态一致性，减少手动地址和独立监听概念。
3. 再做新机器安装/驱动与服务引导、依赖完整性、签名和升级恢复。
4. 最后扩展并发/多节点矩阵和媒体安全统一；无需为了统一而把所有数据塞进控制TLS。
