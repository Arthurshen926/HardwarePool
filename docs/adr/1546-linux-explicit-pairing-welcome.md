# ADR 1546: Explicit finite Linux pairing welcome

Status: experimental private-channel host mode and mandatory isolated acceptance.
Builds on ADRs 1540–1545 and the existing EnrollmentManager protocol.

## Scope

The feature-gated `linux-pairing` management command accepts an explicit
`welcome` action to complement join. Nothing starts merely by launching the
Node, selecting the staged paired profile, listing metadata or inspecting help.
There is no service installation, firewall adjustment, auto-restart, credential
import, discovery observation or resource grant. A valid welcome action opens
one finite enrollment listener at the caller's concrete bind address.

`EnrollmentManager::welcome_manual` uses the same identity generator, PIN
exchange, authentication and bilateral prepare/save receipts as existing welcome.
Manual mode disables discovery announcements and closes the accept listener
immediately after selecting the first connection. The original welcome API
retains its announcement policy and listener lifetime for existing Windows/Android callers.
No new cryptography or cross-device protocol is introduced.

The caller chooses its local NodeId, existing owner-only state and explicit
protected backend. A fresh identity is generated by the existing core during
an accepted attempt; no credential is persisted until the authenticated peers
both approve. Actual operation establishes persistent trust and needs deliberate
human action. Development/CI uses only synthetic temporary identities, owned
private buses and fake keyrings, never user devices or credentials.

## Separate secret invitation channel

The existing exclusive stdin/stdout FIFOs remain the management command/status
channel. They must never carry the host's invitation PIN as output. Instead the
caller provisions a separate existing named FIFO, mode 0600, in an owner-only
0700 directory and opens its reader before sending the welcome request. The
implementation neither creates that FIFO nor changes its permissions.

The path must be absolute, with no symlink traversal; the immediate parent and
FIFO must belong to the current effective UID. The final object must be a
single-link FIFO with exact 0600 mode, not a regular file, socket, terminal or
alias of stdin/stdout/stderr. Opening is nonblocking and fails if no reader is
present. These checks do not protect against a compromised same-user launcher;
exclusive descriptor ownership and trusted local orchestration are prerequisites.

Send the existing length-prefixed JSON frame, for example:

```json
{"version":1,"action":"welcome","name":"Linux node","bind":"127.0.0.1:0","invitation_pipe":"/absolute/owner-only/invitation.fifo"}
```

The loopback bind above is an example for synthetic/local testing, not a remotely
reachable invitation. Real operation requires an explicitly chosen concrete
local interface; wildcard and multicast addresses are rejected. Port zero may
request an ephemeral port. No implicit public address or LAN announcement is
selected, and the command never changes network policy.

Only the separately designated FIFO receives a four-byte big-endian bounded
JSON invitation with `version:1`, `event:"invitation"`, concrete `endpoint`,
eight-digit `pin` and `valid_for_secs`. Validity conservatively reports the
remaining outer deadline, floored to whole seconds after reserving the one-second
write budget; zero remaining validity fails. The fixed overall 180 seconds starts
when the management entry is invoked, not when the invitation is delivered.
Delivery has a one-second write budget within that original deadline.
Failure or a partial write poisons the one-shot invitation channel and cancels
the attempt; it is never retried to another channel.

PINs must not be copied into argv, environment, logs, ordinary stdout/stderr,
metadata files or persistent UI storage. The intended local consumer may display
the secret to the person through its explicitly secured presentation path and
must manage its lifetime. This code adds no UI and cannot erase bytes already
delivered to the caller. Temporary encoded buffers are cleared best-effort;
existing Rust/serde/core copies, compiler erasure, swap and process inspection
are not covered by an audited secure-erasure claim.

## Consent, lifetime and persistence

Ordinary management output contains only sanitized waiting/authentication and
fresh exact-peer confirmation events, never the invitation PIN or endpoint.
Welcome and join share the same approval state machine. The authenticated peer
must match the fresh nonce and peer ID; queued/preplayed, stale, wrong-peer or
replayed approval fails closed. One local approval cannot persist trust without
the peer's independent approval. Existing/revoked records and pending journals
cannot be silently replaced by hosting another attempt.

The first accepted connection consumes the core invitation attempt, including
wrong-PIN or malformed attempts. Additional clients cannot become another
approved peer or cause an automatic new window. Cancel, EOF and fixed expiry
invalidate the attempt, stop its listener and release the manager. Before
bilateral approval no journal or protected credential is written. Once bilateral
persistence begins, cancellation is not rollback; local saved/pending status
retains ADR 1544/1545's honest uncertainty and recovery boundary.

Successful local persistence uses the existing null control-port handoff and
waits for bilateral receipt completion. It starts no media/control service,
grants no source/sink resource and renews no lease. Enrollment completion is
not global readiness or physical-device acceptance. Later finite connections
still require the existing exact pins and independent local/remote approvals.

The authenticated approval phase reads incrementally while awaiting local
consent, using short socket read timeouts within the unchanged overall window.
Peer EOF/cancellation therefore closes a pending confirmation instead of leaving
it alive until expiry. A received approval is not local consent: both the exact
existing peer approval frame and explicit local approval remain prerequisites
for preparation/persistence. Partial frames survive read timeouts; unexpected
bytes fail closed. This is unchanged wire framing, not a new cancellation
message or permission to persist after only one approval.

## Verification

Mandatory hosted tests run two actual Node processes, each with temporary
owner-bound state and its own private fake Secret Service. The invitation moves
only through the dedicated FIFO into the joining process's private input. Both
human decisions are represented explicitly; saved identities and reciprocal
pins, unchanged resource authority, cancellation/expiry, wrong PIN, extra
joiners, backend failure and private-channel validation are checked.

No new management sockets are executed in restricted local environments.
Compilation, pure policy/parser tests and formatting are necessary but do not
replace hosted two-process protocol acceptance. This is not real-keyring vendor
acceptance, real-device pairing, power-loss durability, permission provisioning,
a user-facing onboarding flow or production service deployment.
