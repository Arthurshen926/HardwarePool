# HP-CORE-003 — Operation completion and cancellation seam

Status: complete  
Owner: Codex  
Created: 2026-08-21  
Requirements: `NFR-STAB-002`, architecture section 9

## Objective

Let asynchronous Android, Windows and transport work report typed completion
back into the deterministic Runtime without allowing callback threads to mutate
Core sessions directly.

## In scope

- opaque process-local operation IDs;
- typed start/stop audio operation requests and completions;
- pending, completed, cancelled and disposed states;
- bounded pending and retained-terminal registries;
- Runtime events and snapshots for operation state;
- deterministic race and capacity tests.

## Out of scope

- Android SDK, Kotlin, WASAPI or driver code;
- sockets, async runtimes and background threads;
- changing Core session transitions;
- production error-code or wire-protocol changes;
- permissions, APK deployment or physical-device tests.

## Architecture constraints

- Runtime remains synchronous and operating-system independent.
- Platform callbacks submit typed completions; they never receive mutable Core
  references.
- Every queue and retained collection is explicitly bounded.
- No new production dependency is permitted for this task.

## Acceptance criteria

1. Operation IDs are opaque and generated by Runtime.
2. The registry represents pending, completed, cancelled and disposed states.
3. Pending operations and retained terminal records have independent limits.
4. The first terminal transition wins completion/cancellation races.
5. Start completion records validated actual audio parameters.
6. Runtime snapshots and structured events expose sanitized operation state.
7. Tests cover both race orders, disposal, invalid completion and eviction.

## Implementation plan

1. Add bounded typed operation registry to `hardwarepool-runtime`.
2. Integrate state changes with Runtime events and snapshots.
3. Add deterministic unit and integration tests.
4. Run local CI, document completion and push the reviewed scope.

## Decisions needed

- Stable cross-process/platform error codes remain a separate `HP-CORE-002`
  task; this seam keeps platform failure details out of the public protocol.

## Risks

- A process-local monotonically increasing ID is not a wire identity and must
  not be persisted or reused across Runtime restarts.
- This task creates the callback boundary but does not yet open real audio
  streams.
